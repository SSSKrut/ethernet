# Ethernet MAC на Verilog — 100 Мбит, MII, с ответчиком ARP/ICMP

Учебный проект: **сетевая карта на Verilog**, которая умеет отвечать на `ping`.
Всё написано с нуля (свой MAC + свой мини-стек), проверяется симуляцией на
cocotb, а в перспективе подключается к живому Linux через TAP и реально пингуется.

---

## 0. TL;DR — что здесь есть

```
crc32.v        — движок CRC-32 (один байт за такт), общий для TX и RX
eth_mac_tx.v   — БАЙТЫ кадра  → провод MII (добавляет преамбулу/SFD/FCS)
eth_mac_rx.v   — провод MII   → БАЙТЫ кадра (проверяет FCS)
net_core.v     — «мозг»: смотрит на кадр и отвечает на ARP и ICMP echo (ping)
tests/         — cocotb-тесты (пакеты собираются в Python)
tb_*.v         — те же проверки на чистом Verilog (быстрый smoke)
```

Данные всегда ходят **байтовым потоком** с рукопожатием `valid/ready` (как в
твоём `matmul`): источник поднимает `valid`, приёмник — `ready`, байт «прошёл»
на такте, где оба высокие.

## 1. Мысленная модель: кто что делает

Главное, что путает новичков: **в Verilog ты делаешь НЕ «весь Ethernet»**, а
только один слой. Физику (аналог, витую пару) делает отдельная микросхема — PHY.

```
┌───────────────────────────────────────────────┐
│  твоя логика / протоколы   (net_core.v)        │  ← Verilog
├───────────────────────────────────────────────┤
│  MAC: кадрирование + CRC    (eth_mac_tx/rx.v)  │  ← Verilog, ГЛАВНАЯ работа
├───────────────────────────────────────────────┤
│  MII — цифровой стык (4 бита @ 25 МГц)         │  ← пины FPGA ↔ PHY
├───────────────────────────────────────────────┤
│  PHY-чип: кодирование в линию, витая пара      │  ← ВНЕШНЯЯ микросхема
└───────────────────────────────────────────────┘
```

- **MII** — это то, чем MAC разговаривает с PHY: шина `txd[3:0]`/`tx_en` (передача)
  и `rxd[3:0]`/`rx_dv` (приём) плюс тактовый сигнал **от PHY** (25 МГц на 100 Мбит).
- На 100 Мбит за один такт передаётся **4 бита (нибл)**. Значит один байт = 2 такта.
- `tx_clk`/`rx_clk` мы **не генерируем** — их даёт PHY. В симуляции мы их подделываем.

## 2. Как выглядит кадр Ethernet (байтовая карта)

Это самое важное для чтения `net_core.v` — там всё завязано на смещения байт.

### На проводе (то, что реально едет через MII)

```
│ Преамбула │ SFD  │            КАДР L2 (это и есть «кадр»)             │ FCS  │
│ 7×0x55    │ 0xD5 │ DstMAC SrcMAC Type ─── Payload ───                │ CRC32│
   14 ниблов   2н                46..1500 байт                          4 байта
```

- **Преамбула + SFD** — «звонок»: даёт PHY синхронизироваться. MAC их добавляет
  сам (`eth_mac_tx`) и сам съедает при приёме (`eth_mac_rx`).
- **FCS** — контрольная сумма CRC-32 по кадру L2. Тоже добавляет/проверяет MAC.
- Если кадр короче 60 байт — **добивается нулями** (padding), иначе свитч
  выбросит его как «runt».

### Кадр L2 по байтам (нумерация — как в коде net_core)

```
0   6   12  14                                        конец
├───┼───┼───┼──────────────────────────────────────────┤
│Dst│Src│Typ│                Payload                     │
 MAC MAC
```
| Смещение | Поле        | Пример |
|---------:|-------------|--------|
| 0..5     | Dst MAC     | кому   |
| 6..11    | Src MAC     | от кого|
| 12..13   | EtherType   | `0x0806`=ARP, `0x0800`=IPv4 |
| 14..     | Payload     | ARP-пакет или IP-пакет |

### Если внутри ARP (EtherType 0x0806), payload с 14:

| Смещение | Поле | |
|---:|---|---|
| 20..21 | oper | `0x0001`=запрос, `0x0002`=ответ |
| 22..27 | Sender MAC | |
| 28..31 | Sender IP  | |
| 32..37 | Target MAC | |
| 38..41 | Target IP  | «кого ищем» |

### Если внутри IPv4 (EtherType 0x0800), IP-заголовок с 14, ICMP с 34:

| Смещение | Поле | |
|---:|---|---|
| 23 | IP protocol | `1`=ICMP |
| 24..25 | IP header checksum | |
| 26..29 | IP src | |
| 30..33 | IP dst | |
| 34 | ICMP type | `8`=echo request, `0`=echo reply |
| 36..37 | ICMP checksum | |
| 38..39 | ICMP id | |
| 40..41 | ICMP seq | |

> Именно эти числа ты видишь в `net_core.v` (`buf_mem[34]`, `buf_mem[38..41]` и т.д.).
> Теперь понятно, откуда они: это фиксированные позиции полей в кадре.

## 3. Поток данных: путь одного `ping`

```
   Linux                                                        Linux
   ping 10.0.0.2                                    видит echo reply
      │                                                      ▲
      ▼                                                      │
 ┌────────┐   MII    ┌──────────┐          ┌──────────┐  MII ┌────────┐
 │        │─ nibbles→│eth_mac_rx│─ байты  →│ net_core │─────→│eth_mac_│
 │ провод │          │ (приём)  │  +crc_ok │ (мозг)   │ байты│  tx    │
 │        │          └──────────┘          └──────────┘      └────────┘
 └────────┘
```

1. **eth_mac_rx** ловит преамбулу, собирает нибблы в байты, проверяет CRC,
   складывает кадр в буфер и дёргает `frame_done` + `crc_ok`.
2. **net_core** копирует кадр к себе, смотрит EtherType/поля:
   - ARP-запрос про наш IP → строит ARP-ответ;
   - ICMP echo request на наш IP → строит echo reply.
   Ответ он отдаёт **байтовым потоком** в передатчик.
3. **eth_mac_tx** буферизует ответ, добавляет преамбулу/SFD, считает CRC,
   добивает паддингом и гонит нибблами обратно в MII.

Ключевая идея `net_core`: **«скопировать запрос → на выдаче подменить нужные
байты»**. Ответ на 90% совпадает с запросом, меняется горстка полей.

## 4. Модули по отдельности

### `crc32.v` — движок CRC-32
Чистая комбинаторика: `(crc_in, data_byte) → crc_out` за один байт (8 сдвигов,
отражённый полином `0xEDB88320`). Начальное `0xFFFFFFFF` и финальная инверсия —
снаружи. Контроль: `CRC32("123456789") = 0xCBF43926` (стандартная величина).
Используется и в TX (генерация FCS), и в RX (проверка).

### `eth_mac_tx.v` — байты → MII
Автомат `S_IDLE → S_PRE → S_SFD → S_DATA → S_FCS → S_IFG`.
- `S_IDLE`: принимает кадр в буфер (`s_valid/s_ready/s_last`).
- дальше выдаёт преамбулу, SFD, данные (добивая до `MIN_LEN=60`, попутно считая
  CRC), 4 байта FCS (младшим байтом вперёд), паузу IFG.
- Каждый байт уходит **младшим ниблом вперёд**: `txd = nib ? data[7:4] : data[3:0]`.
- Почему буфер, а не «на лету»: поток MII **нельзя останавливать посреди кадра**
  (это как в `matmul` — сначала загрузка, потом выдача).

### `eth_mac_rx.v` — MII → байты
Автомат `S_IDLE → S_PRE → S_DATA`.
- ждёт `rx_dv`, глотает преамбулу, ловит **SFD по ниблу `0xD`**;
- собирает нибблы в байты, считает CRC по **всему кадру включая FCS**;
- для целого кадра остаток CRC равен константе `CRC_RESIDUE = 0xDEBB20E3` — так
  `crc_ok` получается без отдельного пересчёта;
- кадр лежит в буфере, читается через `rd_addr → rd_data`; `frame_len` — длина
  без FCS.

### `net_core.v` — мозг (ARP + ICMP)
Автомат `N_IDLE → N_COPY → N_CLASS → N_SEND`, параметры `OUR_MAC`, `OUR_IP=10.0.0.2`.
- `N_COPY`: копирует кадр из буфера rx к себе.
- `N_CLASS`: классифицирует (см. байтовую карту выше) — ARP-запрос к нам? ICMP
  echo к нам? иначе молчит.
- `N_SEND`: отдаёт ответ, подменяя на лету нужные байты:
  - **ARP:** переставляет sender/target, `oper=2`, наш MAC/IP как sender.
  - **ICMP:** меняет местами Eth src/dst и IP src/dst; `type 8→0`.

Две приятные хитрости в ICMP-ответе:
- **IP-сумма не меняется** при перестановке src/dst — сумма 16-битных слов
  не зависит от порядка одинаково выровненных полей. Пересчитывать не надо.
- **ICMP-сумму** правим инкрементально: поменялся только `type` (`0x0800→0x0000`),
  поэтому `checksum += 0x0800` со свёрткой переноса (см. `icmp_new`). Полный
  пересчёт не нужен.

## 5. Хитрости, которые встречаются в коде

| В коде видишь | Что это |
|---|---|
| `txd = nib ? d[7:4] : d[3:0]` | MII шлёт байт двумя ниблами, младший первым |
| `4'hD` в приёмнике | это старший нибл SFD `0xD5` — маркер начала данных |
| `32'hEDB88320` | отражённый полином CRC-32 |
| `32'hDEBB20E3` | «магический» остаток CRC для целого кадра |
| `struct.pack("<I", zlib.crc32(...))` в тестах | FCS = zlib CRC32, младшим байтом вперёд |
| `send_idx[2:0] - 3'd6` | выбор байта нашего MAC по позиции (узкий индекс для verilator) |

## 6. Как запускать

```bash
make lint      # verilator -Wall по всем модулям
make test      # cocotb: eth_mac_tx, eth_mac_rx, net_core (основной путь)
make test-v    # быстрый smoke на чистом Verilog (tb_*.v)
make clean
```

Отдельный модуль на cocotb:
```bash
make -C tests DUT=net_core     # или eth_mac_tx / eth_mac_rx
```

Тесты (`tests/`): `eth.py` собирает ARP/ICMP-кадры и суммы; `test_net_core.py`
проверяет ответы (Python играет обе стороны движка), `test_eth_mac_tx/rx.py` —
кадрирование и CRC.
